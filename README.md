# Comprehensive Technical and Experimental Report of the RL + Bucket Routing Framework

The RL + Bucket project is a modular research implementation designed to investigate adaptive and failure-resilient payment routing in Lightning-style payment channel networks. The repository combines graph-based network modeling, heuristic pathfinding, fixed Top-K candidate generation, reinforcement learning, bounded candidate storage through a Bucket mechanism, probabilistic payment failure modeling, payment simulation, and partial backtracking into a single experimental routing pipeline. Rather than allowing a reinforcement-learning agent to construct an entire payment path node by node, the framework uses reinforcement learning to control an adaptive routing parameter, while the actual candidate paths are generated by deterministic graph algorithms. This separation is an important characteristic of the implementation because it combines the adaptability of reinforcement learning with the structural guarantees and interpretability of conventional graph-based routing.

At the network layer, the framework represents the Lightning-style payment network as a NetworkX MultiDiGraph. The use of a directed multigraph is important because a payment channel network cannot always be represented correctly by a simple undirected graph. A pair of nodes may have multiple parallel channels, and the two directions of a channel may have different routing conditions. Consequently, the implementation attempts to preserve channel-level identity, including channel keys and channel identifiers, instead of reducing parallel channels to a single edge. This design is particularly relevant for Lightning Network routing because two channels connecting the same pair of nodes should not automatically be considered interchangeable. The pathfinding and simulation components therefore operate on channel-specific edge information whenever such information is available.

The network construction functionality is concentrated in the graph-building layer, particularly in the `Network/graph_builder.py` module and the `LNGraphBuilder` class. This component provides several ways of constructing the network. It can construct a graph from converted real-world snapshot data, from in-memory data structures, and from synthetic graph specifications. The builder also provides basic network-level information such as the number of nodes, the number of channels, and a graph summary. This creates a common representation for the rest of the project, so that pathfinding, reinforcement learning, simulation, and evaluation do not have to independently implement network parsing.

The repository also supports real Lightning-style snapshot data. The project has been tested with GML-based snapshots such as `20190501.gml.geo`. The original snapshot contains approximately 4,143 nodes and 33,195 undirected edges. When represented as directed channels in the MultiDiGraph model, this corresponds to approximately 66,390 directed channel records. This conversion is important because subsequent routing operations are directional. The graph builder therefore provides the bridge between the original snapshot representation and the directed graph representation required by the routing pipeline.

## Spatial carbon data and paired evaluation

For the current study, the existing country-level 2021 carbon data is the chosen input and is sufficient. RGB is not used as a carbon proxy. A finer GeoJSON polygon layer remains optional; the current run does not require one.

Directional liquidity is hidden simulator state. When a snapshot supplies reciprocal channel directions and a capacity, the simulator samples one seeded uniform split of that capacity between the two directions. It keeps the sampled balances outside the public graph. If a snapshot has no capacity, the configured `channel.default_capacity` supplies the simulation's structural bound; for `20190501.gml.geo` this is currently 1,000,000. This is an explicit simulation assumption, not a measured channel capacity or a claim about the historical network. Routing does not reject an unknown-liquidity channel. After an observed liquidity failure or successful payment, the environment updates per-direction lower and upper bounds and exposes those bounds to PPO in the next observation. The state vector now has 180 values (previously 165), so PPO models trained with the old observation shape must be retrained.

The paired ablation runner compares four arms on the exact same held-out transaction ordering and scenario seeds: static LND baseline, RL-only, Bucket-only with fixed LND eta, and RL+Bucket. All arms use the same seeded hidden-liquidity split for each scenario. The configured research run uses 3,000 held-out transactions, five repetitions, and each configured failure rate (1–6%). It reports transaction success, mean route delay, p90/p95 delay for successful routes and all routed payments, fees, carbon, and repetition-level 95% Student-t confidence intervals. It also reports paired repetition-level differences against the baseline for success and p95 delay. Route delay here is the sum of the edge delay/CLTV values in the selected path. With the current five repetitions, confidence intervals should be read as estimates, not substitutes for more seeds.

Retrain PPO with the expanded 180-value observation before evaluation:

```powershell
$env:RL_FAST_VALIDATION = "0"
python main.py
```

The training run writes the new model to `models/end_to_end_hidden_failure_blind.zip`, which is also the ablation runner's default model path.

When `RL_FAST_VALIDATION=1` (the default), the end-to-end runner first tries that checkpoint. If it is missing or incompatible, it trains a 16-step PPO model under `models/fast_validation/` and continues the smoke run. Set `RL_QUICK_TIMESTEPS`, `RL_QUICK_N_STEPS`, and `RL_QUICK_BATCH_SIZE` to adjust this quick run. The model is kept separate from the research checkpoint, and the report marks the resulting metrics as smoke-validation output rather than scientific evidence.


The runner expects `20190501.gml.geo` and `models/ppo_lightning_eta.zip` in the project root by default. Use `--snapshot`, `--model`, and `--output-dir` to choose other paths. It writes paired transaction rows to CSV and summary metadata/results to JSON under `Evaluations/results/paired_ablation` by default. The four-arm runner requires a trained PPO model even for arms that do not use its policy, because that model is used by the RL-only and RL+Bucket arms.

An important modeling decision in the graph-building layer is the distinction between advertised channel capacity and directional liquidity. The implementation does not treat a channel's static capacity as if it were a known directional balance. This distinction is essential because a public Lightning Network snapshot generally does not reveal the exact current directional balance of every channel. The graph representation can therefore retain static channel capacity while leaving `balance_uv` and `balance_vu` unknown when directional information is unavailable. Optional estimated liquidity fields can subsequently be populated by another component or learning process. This prevents the routing system from making the incorrect assumption that the entire advertised capacity is simultaneously spendable in either direction.

The graph-building layer preserves geographic and visual metadata when available. RGB remains visual metadata and is never converted into carbon intensity. Carbon intensity is resolved from node coordinates against an optional root-level `carbon_intensity.geojson` GeoJSON `FeatureCollection` containing Polygon or MultiPolygon features with a `carbon_intensity` property (gCO2/kWh). A matched feature may include `year` and `spatial_resolution` properties. When no spatial feature covers a node, the builder uses the country value in `global_energy_mix.json`, then continent and world averages. Every node records `carbon_intensity_source`, `carbon_intensity_resolution`, and `carbon_intensity_year`, so a country average is not presented as a point-level observation. The current root dataset contains country-level values for 2021; without a supplied spatial GeoJSON layer, the project still has country-level spatial resolution.

The `Network/topology` layer complements the graph builder by providing topology-related features used by the routing and state representation components. These features allow the routing process to incorporate structural properties of the network rather than relying exclusively on basic channel cost. The topology layer is particularly relevant to the project's attempt to combine conventional routing criteria with adaptive information derived from the surrounding graph.

The pathfinding layer contains the deterministic routing mechanisms that generate actual candidate paths. Its major components include `Pathfinding/heuristics.py`, `Pathfinding/dijkstra.py`, and `Pathfinding/top_k_paths.py`. These modules work together but have distinct responsibilities. The heuristic layer calculates routing-related penalties and adaptive costs, the Dijkstra implementation searches for a minimum-cost path under those costs, and the Top-K implementation extends this process to produce a bounded collection of alternative candidate paths.

The heuristic module is responsible for constructing the adaptive routing cost used by the pathfinding algorithms. The central idea is that the original LND-style routing cost can be modified using an adaptive penalty. The project uses the formulation `C'(e) = C_LND(e) * (1 + lambda_h * penalty)`, where `C_LND(e)` represents the base routing cost associated with an edge, `penalty` represents additional routing information, and `lambda_h` controls the contribution of the heuristic penalty. The implementation constrains `eta` to the interval from zero to one, while the heuristic coefficient is required to remain non-negative. The same adaptive cost formulation is intended to be used consistently by both Dijkstra and Top-K path generation so that candidate paths are not generated under one cost definition and evaluated under another.

The Dijkstra module provides the fundamental shortest-path operation. Given a source, destination, graph, and routing parameters, it evaluates the network according to the configured edge cost and produces a candidate route. Dijkstra is therefore not the reinforcement-learning component itself. Instead, it is one of the deterministic mechanisms through which the RL-controlled routing parameter influences actual path generation. The reinforcement-learning agent does not directly manipulate individual nodes in the path. It modifies the routing behavior through `eta`, after which Dijkstra and the subsequent Top-K procedure determine concrete routes.

The Top-K pathfinding module extends the single-route Dijkstra operation by generating a bounded collection of alternative paths. The current project configuration uses a fixed value of five for `top_k_paths`. Therefore, the framework is not currently allowing the PPO agent to select an arbitrary value of K. Instead, K remains fixed at five, while the reinforcement-learning agent controls the adaptive routing parameter. This separation makes the experimental interpretation clearer because changes in routing outcomes can be associated primarily with the learned adaptive parameter rather than simultaneous changes in both K and the routing metric.

The Top-K layer is particularly important for the Bucket mechanism. Rather than immediately committing to the first route returned by a shortest-path algorithm, the framework generates several candidates. These candidates can then be evaluated by the Bucket and payment simulation layers. This creates a controlled form of route diversity. The route candidates can contain channel-specific information such as source, target, channel key, SCID, and associated edge data. Preserving this information is necessary because parallel channels can otherwise become indistinguishable during subsequent simulation and backtracking.

The reinforcement-learning layer is implemented in the `RL` package. Its major components include `RL/state.py`, `RL/environment.py`, `RL/reward.py`, `RL/ppo_agent.py`, and `RL/train.py`. Together these modules define the observation representation, environment interaction, reward calculation, PPO agent, and training procedure. The project uses Proximal Policy Optimization as its reinforcement-learning algorithm.

The `RL/state.py` module is responsible for constructing the state representation supplied to the agent. The state is not simply a single scalar describing the current transaction. Instead, it incorporates network and neighborhood information derived from the routing context. The current configuration uses a neighborhood size of 15, an additional neighborhood parameter of 5, and an ego radius of 2. These parameters determine how much local network information is incorporated into the observation. The state representation is therefore intended to provide the policy with contextual information about the routing situation while keeping the observation dimension fixed.

The PPO state vector has a dimension of 180: 15 observed channels, each represented by 11 features, plus a 15-element padding mask. Its liquidity features are the agent's learned lower and upper bounds; the simulator's hidden balances and failure probabilities are excluded. The action space is a one-dimensional continuous interval configured by `rl.eta_min` and `rl.eta_max` (currently -1 to 1). The agent outputs this routing-control value rather than a discrete route index.

The `RL/ppo_agent.py` module implements the PPO-based agent and its interaction with Stable-Baselines3. The PPO configuration in the repository uses a learning rate of `0.0003`, a discount factor of `0.99`, a GAE parameter of `0.95`, a clipping range of `0.20`, an entropy coefficient of `0.01`, and two hidden layers of 128 units. The configured training horizon is 20,000 timesteps, with 256 steps per rollout and a batch size of 64. The device is configured as `auto`, allowing the implementation to use an available computational device.

The most important conceptual point in the RL design is that PPO controls `eta` rather than constructing the complete route. The agent receives the routing state and produces an action in the configured `eta` interval. That action modifies the routing heuristic, which then affects Dijkstra and Top-K candidate generation. The policy controls the routing preference while the graph-search algorithm constructs candidate paths.

This approach also provides a useful division between learned and deterministic components. PPO is responsible for adapting the routing parameter according to the observed state and reward history, while Dijkstra and Top-K provide the graph-theoretic mechanism for generating valid paths. Bucket and backtracking then handle route alternatives and failures. The resulting architecture is therefore neither a pure shortest-path algorithm nor a pure end-to-end neural routing model. It is an integrated routing framework in which reinforcement learning modifies a conventional pathfinding process.

The `RL/environment.py` module connects the agent to the rest of the routing system. It acts as the environment through which a routing state is transformed into an action, the action is converted into an adaptive routing parameter, candidate paths are generated, candidates are stored and evaluated, and a final routing outcome is produced. This module is consequently one of the central integration points in the project because it links the RL layer to pathfinding, Bucket management, simulation, and reward computation.

The reward mechanism is implemented in `RL/reward.py`. The reward is designed to distinguish different routing outcomes rather than simply assigning a binary success or failure value. The experimental behavior includes higher rewards for direct successful routing, somewhat lower rewards when backtracking is required, still lower outcomes when a full reroute is necessary, and negative rewards for unsuccessful transactions. This structure provides the PPO agent with information about the quality of the routing outcome rather than only whether a payment eventually succeeded.

The repository's previous experimental outputs illustrate this principle. A normal successful transaction can produce a reward around `0.8407`, while a successful backtracking outcome can receive a lower reward around `0.7707`, and a successful full-reroute outcome can receive approximately `0.7207`. A failed transaction can receive a negative reward, with one observed value around `-0.8483`. These values should be interpreted as the current implementation's reward design rather than universal measures of routing quality.

The `RL/train.py` module provides the training procedure. It brings together the environment and PPO agent and manages the training configuration. The repository also contains mechanisms for faster validation and training through environment variables. These options are useful because training PPO on a real snapshot can be computationally expensive. In one observed experiment with only 256 timesteps, training required several minutes on CPU. The fast-training and validation modes therefore serve as practical mechanisms for debugging and experimental iteration rather than as substitutes for the final configured training process.

The Bucket subsystem is one of the defining components of the project. It contains `Bucket/bucket.py`, `Bucket/candidate_manager.py`, and `Bucket/backtrack.py`. The purpose of the Bucket is to maintain a bounded set of alternative candidate routes rather than immediately discarding all alternatives after the first path has been generated. The current configuration sets the maximum number of candidates to five, matching the Top-K setting.

The candidate manager is responsible for handling the candidate route collection. Candidate paths can be ranked according to their routing scores and stored in the Bucket. This means that the Bucket is not simply a Python list of arbitrary paths. It functions as a controlled candidate-management layer between path generation and payment execution. Candidate identity, score, status, and failure information can be associated with individual routes.

The Bucket also records failed channels or route attempts. This is important because a payment failure should not necessarily cause the entire routing process to start from the beginning. If one candidate fails because a channel cannot forward the payment, the system can attempt another candidate already generated by the Top-K stage. This is the main operational advantage of keeping multiple candidates available.

The `Bucket/backtrack.py` module provides the partial backtracking mechanism. The current configuration enables backtracking and sets the maximum backtracking depth to three. The objective is to recover from a failed route using existing routing alternatives before resorting to a complete rerouting process. Consequently, the project distinguishes between direct successful routing, successful recovery through a Bucket candidate, partial backtracking, and full rerouting.

This behavior is particularly important to the project's failure-resilience objective. A conventional single-path routing process can fail when an intermediate channel becomes unavailable or cannot carry the requested amount. If the router has already generated several alternatives, however, it can attempt another candidate without repeating the entire path-generation procedure. The Bucket therefore acts as a bounded memory of routing alternatives.

The reported field `Successful Bucket route: 3 / 5` should be understood in this context as identifying the successful candidate within the five stored candidates. A value of `3 / 5` indicates that the third selected candidate was the successful one among the available five candidates; it does not mean that three of five routes independently succeeded.

The simulation layer is responsible for determining whether a generated candidate can actually execute a payment under the simulated network conditions. Major modules include `Simulation/payment_simulator.py`, `Simulation/failure_model.py`, `Simulation/network_dynamics.py`, `Simulation/onion.py`, `Simulation/router.py`, `Simulation/transaction_generator.py`, and `Simulation/backtrack.py`.

The `Simulation/transaction_generator.py` module is responsible for creating payment transactions used during experiments. The configured simulation amount range is from 1,000 to 1,000,000 units. Transactions can use different source and destination nodes and different payment amounts, allowing the routing pipeline to be tested under multiple conditions. The current experimental workflow can also be configured to execute multiple randomly generated transactions in a single run, which is useful for producing a collection of routing outcomes instead of evaluating only one fixed transaction.

The `Simulation/payment_simulator.py` module represents the execution stage. Once candidate routes have been produced, the simulator attempts to forward the payment along the selected route. It evaluates the route against the simulated channel and failure conditions and returns the resulting payment outcome. This separates path generation from path execution. A path can therefore be graph-theoretically valid while still failing during payment execution, which is precisely the condition that makes the Bucket and backtracking mechanisms meaningful.

The `Simulation/failure_model.py` module models routing failures probabilistically. The configuration defines failure rates ranging from one to six percent. These failure probabilities provide a controllable mechanism for evaluating how the routing framework behaves as network reliability changes. Because the project is primarily an experimental simulator rather than a live Lightning Network router, these failures should be interpreted as modeled experimental events rather than measurements of actual current Lightning Network failure rates.

The `Simulation/network_dynamics.py` module represents changes in network conditions that may affect payment routing. This is important because a routing decision that is valid at one point in time may not remain valid after a payment attempt or network event. The dynamics layer therefore contributes to the project's attempt to evaluate routing under changing conditions rather than assuming a completely static graph.

The `Simulation/router.py` module coordinates routing operations at the simulation level. It provides the interface through which generated candidate paths can be passed to the payment execution process. It helps separate routing logic from the lower-level mechanics of payment execution.

The `Simulation/onion.py` module represents the Onion-style forwarding aspect of the payment process. It provides a simulation abstraction for forwarding information through intermediate nodes rather than treating a route as a simple list that is automatically successful. This contributes to making the payment simulation more representative of a multi-hop payment process.

The `Simulation/backtrack.py` module provides another backtracking-related layer within the simulation subsystem. Its role is distinct from the higher-level Bucket backtracking logic. The Bucket determines which existing candidate should be considered next, while the simulation-level backtracking mechanisms handle the execution consequences of failed forwarding attempts. The interaction between these layers allows the project to model recovery from failures without immediately discarding all existing routing information.

The evaluation layer provides the experimental interface for comparing the proposed routing method with baseline routing strategies. The `Evaluations/baselines.py` module defines several baseline configurations, including native and static variants associated with LND, CLN, and ECL. The baseline logic uses a deterministic Dijkstra-based route and executes a single selected route through the payment simulator. It does not use the Bucket, PPO RoutingEnv, or the proposed partial-backtracking pipeline.

The proposed method in the evaluation layer follows the integrated sequence of PPO, adaptive `eta`, Top-K candidate generation, Bucket management, payment simulation, and partial backtracking. This distinction is essential for a fair interpretation of experimental results. The baseline is not simply another name for the proposed system with reinforcement learning disabled. The baseline follows a different execution path, centered on selecting one route through deterministic routing and then executing it.

The evaluation output records a relatively broad set of metrics. These include transaction identifiers, the selected `eta`, the Top-K value, the number of generated candidates, the number of usable candidates, Bucket size, payment success, path information, path length, fee, delay, carbon-related metric, failure probability, average delay, backtracking count, partial-backtracking success, full-reroute information, attempt count, failure or success reason, episode reward, inter-country hops, inter-continent hops, runtime, recovery status, and payment amount. This set of measurements allows the project to evaluate not only whether a payment succeeds but also how the system reached that outcome.

The evaluation configuration currently specifies ten repetitions and a 95 percent confidence interval. The project configuration also defines 10,000 transactions, with a 70 percent training ratio and a 30 percent test ratio. These values describe the configured large-scale experimental setting, whereas fast-validation runs may intentionally use smaller workloads to reduce execution time during development and debugging.

The `Configs/config.yaml` file provides a central definition of the major experimental parameters. The graph configuration includes a synthetic network size of 250 nodes, 500 additional synthetic edges, a maximum hop count of 12, five Top-K paths, a neighborhood size of 15, a secondary neighborhood parameter of 5, and an ego radius of 2. The channel configuration specifies default capacity, base fee, fee rate, and CLTV delta values. The simulation configuration defines amount bounds, retry behavior, the probabilistic failure model, reward scaling, and a carbon-related numerical epsilon. The RL section specifies PPO and its training hyperparameters, while the Bucket section defines its capacity, selection strategy, and backtracking behavior.

The project also contains testing infrastructure intended to verify individual components before performing complete end-to-end experiments. This is important because the repository contains several interacting subsystems, and a failure in one module can otherwise appear to be a reinforcement-learning problem when it is actually a graph-format or simulation-interface problem. Unit and integration tests have therefore been used to verify sensitive modules such as graph construction, pathfinding, candidate representation, Bucket behavior, and simulation logic.

One important testing concern has been preserving the distinction between MultiDiGraph edges and ordinary graph tuples. A conventional graph representation may describe an edge as `(source, target)`, whereas a MultiDiGraph requires an additional channel key to uniquely identify a parallel channel. The project therefore uses richer candidate representations containing information such as `source`, `target`, `channel_key`, `scid`, and `data`. Maintaining this structure through Dijkstra, Top-K, Bucket, and simulation is necessary to prevent a valid channel from being accidentally replaced by another parallel channel.

The repository also addresses malformed or incomplete liquidity information. Because real snapshot data does not necessarily expose current directional balances, the routing implementation must avoid converting unknown liquidity into false certainty. Explicitly known liquidity can be represented and processed, while unavailable directional liquidity remains unknown. This design is more appropriate for experiments based on historical public snapshots than assuming that every channel's advertised capacity represents its current usable balance.

The main execution layer, represented by `main.py`, acts as the integration point for the complete experiment. It coordinates configuration loading, graph preparation, model loading or training, routing execution, simulation, and reporting. One important part of the intended workflow is the ability to accept a `.gml.geo` snapshot and perform the conversion inside the main execution process before passing the resulting graph data into `LNGraphBuilder`. This keeps snapshot conversion separate from the actual graph-building abstraction while still allowing the end-to-end command to operate directly on the original snapshot.

The complete conceptual execution flow can therefore be described as follows. A network snapshot is loaded and converted into the internal graph representation. The graph builder constructs a directed multigraph while preserving channel identity and relevant network metadata. A transaction generator or evaluation procedure selects a source, destination, and payment amount. The RL state module constructs the observation for the PPO agent. PPO produces a continuous action corresponding to `eta`. The adaptive heuristic interprets this parameter and modifies the routing cost. Dijkstra and Top-K then generate up to five candidate paths. The candidate manager places these paths into the Bucket. The payment simulator attempts the selected candidate. If the candidate succeeds, the transaction terminates successfully. If it fails, the system can record the failed channel and attempt another candidate or invoke partial backtracking. Only when the available alternatives cannot recover the payment does the execution progress toward a full reroute or final failure. The resulting routing outcome is then converted into a reward and recorded by the evaluation system.

This structure means that the reinforcement-learning agent is not expected to learn the complete topology of the network from scratch. The graph algorithms already provide valid candidate routes, while the RL component learns how the routing cost should be adapted to the observed context. This reduces the action space substantially compared with a formulation in which the agent must select every next hop. It also provides a clearer experimental separation between learning-based adaptation and deterministic path construction.

The repository's design additionally allows `eta` to be tested at boundary values. Testing `eta = 0` provides a condition in which the adaptive contribution is minimized, while `eta = 1` provides the opposite boundary of the defined parameter range. Such boundary tests are useful because they verify that the adaptive mechanism actually changes routing behavior and that the implementation does not silently collapse all values of `eta` into the same routing configuration.

The training and evaluation stages must nevertheless be distinguished. A short PPO run used for debugging should not be interpreted as equivalent to the configured 20,000-timestep training experiment. In earlier validation runs, PPO training with only 256 timesteps produced a valid model and actions in the expected interval, but some transactions generated zero usable candidates and negative rewards. This demonstrates that successful model loading and action generation do not by themselves prove successful routing. The complete pipeline must be evaluated from candidate generation through payment execution.

The zero-candidate condition is particularly important for interpreting experimental results. An RL action can be numerically valid while the downstream pathfinding process produces no usable candidate for the selected source-destination transaction. Therefore, the meaningful unit of evaluation is the complete routing transaction, not merely the PPO output. Candidate count, usable candidate count, Bucket size, payment result, backtracking behavior, and final reward must be considered together.

The framework also provides a distinction between computational validity and experimental validity. Computational validity concerns whether individual modules execute correctly, preserve their data structures, and communicate through compatible interfaces. Experimental validity concerns whether the resulting routing behavior supports the intended research conclusions. Passing unit tests establishes the first property but does not automatically establish the second. The current transition from module-level debugging toward complete end-to-end execution is therefore an important stage of the project.

From an experimental perspective, the framework is designed to investigate several dimensions of routing behavior simultaneously. Payment success measures whether a transaction can be completed. Failure resilience measures whether a failed initial route can be recovered using existing candidates or partial backtracking. Fee and delay quantify conventional routing costs. The carbon-related metric introduces an additional network attribute derived from the graph metadata. Candidate counts and Bucket size measure how much routing flexibility is available. Backtracking and retry counts measure the effort required to recover from failures. Runtime measures computational overhead. The PPO reward combines these routing outcomes into the learning signal used by the adaptive agent.

The repository also contains baseline-oriented evaluation logic that makes it possible to distinguish the contribution of the proposed RL + Bucket mechanism from deterministic LND-style routing. In such a comparison, it is important not to attribute every observed improvement to PPO alone. The proposed pipeline contains several interacting mechanisms: adaptive heuristic control, Top-K candidate generation, Bucket-based candidate management, payment simulation, and partial backtracking. Consequently, an observed difference between a baseline and the complete proposed method represents the effect of the integrated routing pipeline unless additional ablation experiments isolate the individual components.

For this reason, a scientifically stronger interpretation of the system separates the contributions into at least three conceptual levels. The first is deterministic routing based on the underlying LND-style cost. The second is multi-candidate routing through Top-K and Bucket management. The third is adaptive routing through PPO-controlled `eta`. Partial backtracking and probabilistic failure handling then provide the mechanism through which the framework evaluates resilience under failed payment attempts. This decomposition makes it possible to explain what the system actually contributes without incorrectly attributing the behavior of the entire pipeline to the neural policy.

The repository's experimental limitations should also be stated explicitly. The system operates on network snapshots and simulated payment conditions rather than directly executing payments on the live Lightning Network. Directional liquidity is generally unavailable in historical snapshots and is therefore not treated as directly known. The failure model uses configurable probabilities rather than a direct measurement of current channel-level failure statistics. The carbon metric is the average grid carbon intensity associated with route nodes; it is not a measurement of the electricity used by a transaction or its actual emissions. Its spatial precision is limited by the input layer: the currently supplied 2021 data is country-level, and coordinate-level estimates require a spatial GeoJSON layer. Onion routing and payment forwarding are simulated abstractions. These characteristics define the scope in which the experimental results should be interpreted.

Another important limitation concerns the relationship between historical topology and dynamic network behavior. A snapshot provides a representation of network structure at a particular point in time, but the real Lightning Network changes continuously. Therefore, results obtained from a historical snapshot should be described as simulation results under the corresponding topology and experimental assumptions. They should not automatically be interpreted as measurements of current live-network performance.

The project's architecture nevertheless provides a useful research framework because it explicitly combines adaptive decision-making with deterministic routing and bounded recovery. PPO supplies a learned routing-control parameter; heuristic functions translate that parameter into a graph cost; Dijkstra and Top-K generate actual candidate paths; the Bucket preserves a bounded set of alternatives; the payment simulator tests those alternatives under modeled failures; and partial backtracking provides a recovery mechanism. Evaluation then records the complete transaction outcome and feeds routing performance back into the learning process.

Overall, the RL + Bucket repository implements a complete experimental routing pipeline rather than an isolated reinforcement-learning model. Its central contribution in the current implementation is the integration of a PPO-controlled adaptive routing parameter with conventional graph-based pathfinding, fixed Top-K candidate generation, bounded Bucket storage, probabilistic payment failures, and partial backtracking. The architecture preserves channel-level information through a MultiDiGraph, avoids equating advertised capacity with directional liquidity, separates candidate generation from payment execution, and records multiple dimensions of routing performance.

The complete system can therefore be understood as an adaptive and failure-resilient routing framework in which learning determines how routing preferences should adapt to the current state, while deterministic algorithms maintain control over actual path construction and candidate validity. The Bucket mechanism then provides a bounded memory of alternative routes, allowing the system to recover from failures without immediately discarding previously generated routing information. This combination creates a clear experimental basis for studying whether adaptive routing decisions and candidate-based recovery can improve payment-routing behavior under simulated failure conditions while maintaining measurable control over cost, delay, carbon-related attributes, routing complexity, and computational overhead.
